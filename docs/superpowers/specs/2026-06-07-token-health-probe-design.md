# 账号令牌健康探测设计

## 背景

当前系统已经有账号运行健康、站点可访问性、令牌模型覆盖和路由通道可用性等机制，但账号令牌管理页无法直观看到单个令牌本身是否可用。

这些概念不能混用：

- 账号健康只表示账号级连接状态，不代表账号下每个令牌可用。
- 令牌健康只表示该令牌能否成功发起一次最小上游请求，不代表该令牌支持所有内部模型。
- 模型覆盖表示某个令牌支持哪些模型。
- 路由可用性还会叠加站点、账号、通道冷却、额度冷却、权重、优先级等运行时因素。

本设计将新增独立的令牌健康探测机制，并在账号令牌管理中展示。

## 目标

1. 在账号令牌管理列表显示每个令牌的独立健康状态。
2. 令牌健康探测只使用一个代表模型，降低探测成本。
3. 支持按令牌配置探测模型，同时允许继承站点和全局默认。
4. 使用真实业务请求作为健康信号，避免对最近成功使用的令牌重复探测。
5. 业务请求失败后将对应令牌加入定时探测队列，直到恢复或持续失败。
6. 保留现有令牌模型覆盖机制，不把模型覆盖误当成令牌健康。

## 非目标

- 不用一次令牌健康探测证明所有模型都可用。
- 不替代现有 `token_model_availability` 的模型覆盖数据。
- 不把路由选择概率直接写入令牌健康状态。
- 不要求每个令牌都手工配置探测模型。

## 状态模型

账号令牌新增健康读模型，列表展示以下状态：

- `可用`：最近业务请求成功，或最近探测成功。
- `待探测`：令牌可用性数据不存在或已经过期。
- `业务失败待复检`：真实业务请求使用该令牌失败，等待定时探测确认。
- `探测失败`：定时或手动探测失败。
- `不可探测`：令牌禁用、缺少完整令牌值、`valueStatus` 非 `ready`、账号或站点禁用。

状态展示需要包含：

- 状态标签。
- 最近成功时间。
- 最近失败时间。
- 最近失败原因摘要。
- 使用的探测模型，标明是令牌自定义、站点继承还是全局继承。

## 探测模型配置

配置采用三层继承：

1. 令牌专属探测模型。
2. 站点默认探测模型。
3. 全局默认探测模型。

最终生效规则：

```text
令牌探测模型 > 站点探测模型 > 全局探测模型
```

令牌编辑界面提供：

- `继承默认`。
- `自定义模型`。

当令牌自定义模型为空或无效时，回退到继承默认。页面应展示最终生效模型和来源，避免用户误以为没有配置。

## 探测方法

探测请求应使用最省 token 的方式：

- 非流式请求。
- 最小输入，例如 `"1"`。
- 输出上限设为 1 token。
- 能关闭 reasoning、工具调用、额外输出时尽量关闭。
- 只判断请求是否成功以及响应是否可解析，不评估内容质量。

探测服务复用现有上游 endpoint 解析和请求构造能力，确保不同平台、OAuth、API Key、sub2api/newapi 端点逻辑保持一致。

## 定时调度

连接维护任务增加令牌健康探测阶段，或在现有连接维护模型覆盖阶段旁边新增独立阶段。

定时任务只探测满足以下任一条件的令牌：

- 从未探测过。
- 健康数据超过过期阈值。
- 最近真实业务请求失败。
- 上次探测失败，且已经到达重试时间。

定时任务跳过以下令牌：

- 令牌被禁用。
- 账号或站点被禁用。
- 令牌值不可用或处于脱敏待补全状态。
- 最近真实业务请求成功且健康数据未过期。

失败重试沿用连接维护中“重试 5 次失败才算真的失败”的原则。单次网络抖动不应立刻把令牌标成长期不可用。

## 真实请求反馈

代理请求成功时：

- 如果请求使用了账号令牌，则刷新该令牌健康状态为 `可用`。
- 更新最近成功时间和使用模型。
- 该令牌在健康数据过期前免于定时探测。

代理请求失败时：

- 如果失败可以归因到具体账号令牌，则记录最近失败时间和失败原因摘要。
- 状态更新为 `业务失败待复检`。
- 该令牌进入后续定时探测队列。

错误归因应只记录摘要，不保存完整请求体、明文 token 或敏感响应。

## UI 展示

账号令牌管理列表新增健康信息：

- 健康状态标签。
- 探测模型。
- 最近成功或失败时间。
- 失败原因摘要。

令牌详情或编辑弹层显示：

- 探测模型配置。
- 生效配置来源。
- 最近探测结果。
- 最近业务成功/失败记录。
- 模型覆盖摘要：支持模型数、不支持模型数、未测模型数。
- 关联路由状态入口，说明路由可用性不等同于令牌健康。

## API 边界

`/api/account-tokens` 响应扩展令牌健康摘要字段。

账号令牌更新接口支持更新令牌专属探测模型。

新增或扩展手动探测接口：

- 支持按 `tokenId` 触发令牌健康探测。
- 支持等待结果或后台任务两种模式。
- 手动探测不刷新模型覆盖，只刷新令牌健康。

设置接口支持全局默认探测模型。站点接口支持站点默认探测模型。

## 数据持久化

需要持久化两类数据：

1. 探测模型配置：
   - 令牌专属探测模型。
   - 站点默认探测模型。
   - 全局默认探测模型。

2. 令牌健康状态：
   - 当前状态。
   - 最近成功时间。
   - 最近失败时间。
   - 最近失败原因摘要。
   - 最近探测时间。
   - 最近探测模型。
   - 下次可重试时间或失败计数。

实现时可以选择新增独立 `account_token_health` 表，避免继续扩大 `account_tokens` 表职责。令牌配置字段可以放在 `account_tokens`，因为它是令牌自身属性。

## 测试重点

- 令牌专属、站点默认、全局默认探测模型继承顺序。
- 禁用令牌、脱敏令牌、禁用账号、禁用站点不会进入探测队列。
- 最近业务请求成功的令牌不会被重复定时探测。
- 业务请求失败会把令牌标记为待复检。
- 手动探测只更新令牌健康，不误更新模型覆盖。
- `/api/account-tokens` 能返回健康摘要，且不泄露明文 token。
- UI 能展示继承来源和失败摘要。

## 开放风险

- 不同平台的最小请求格式不完全一致，需要复用现有上游请求构造和 endpoint 派生逻辑。
- 某些模型可能不支持极低输出上限，需要允许平台适配层调整最小请求参数。
- 业务请求失败可能由 payload、模型、临时网络、额度或令牌本身导致，健康状态应先进入待复检，而不是直接永久判定不可用。
